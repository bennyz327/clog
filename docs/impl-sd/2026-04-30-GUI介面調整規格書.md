# GUI 介面調整規格書

## 1. 文件目的

本文件定義 `clog` GUI 介面的本次調整範圍，將目前偏向「多清單 + 單一文字詳細區」的主畫面，調整為以「左欄搜尋結果 + 右欄綜合詳細視窗」為核心的操作模式。

本文件屬於實作設計（SD）文件，目的如下：

- 明確定義畫面結構、元件、互動規則與狀態切換
- 將 GUI 層、CLI 層、共用業務層的責任切清楚
- 提供後續實作與驗收依據

## 2. 範圍

本次調整僅涵蓋 GUI 介面與其互動行為，不變更既有資料模型與 CLI 命令語意。

本次範圍包含：

- 主畫面頂部 bar 改為多個下拉式選單排列
- 主畫面 body 重構為左右雙欄
- 右欄重構為系統管理的多 tab 綜合詳細視窗
- `overview` tab 的 UI 與互動定義
- 各維護 tab 的顯示方式與操作守則
- 右下角通知區重構
- 不同視窗尺寸下的 RWD / 自適應顯示策略

本次範圍不包含：

- i18n 切換功能本身
- 新資料表或 schema 調整
- CLI 指令重新設計
- 各維護 tab 的完整 CRUD 欄位細節定稿以外的額外商業規則擴充

## 3. 通用準則

### 3.1 顯示語言

下一步才會製作 i18n 切換，因此本次 GUI 調整一律先以繁體中文為顯示語言，不必保留英文顯示。

### 3.2 分層責任

所有新增或調整的業務操作，仍需嚴格依照 GUI / CLI / 共用業務層三種職責分層實作。

- GUI 層
  - 負責畫面、事件、選取狀態、tab 管理、dialog 開關、右鍵選單
  - 不直接寫資料庫查詢邏輯
- CLI 層
  - 維持原本命令介面，不因 GUI 改版而承擔 GUI 專用狀態
- 共用業務層 / controller / service
  - 負責資料讀寫、驗證、錯誤處理、pubsub、背景工作協調
  - GUI 與 CLI 應盡量共用同一組業務能力

### 3.3 操作一致性守則

各維護 tab 中，單筆資料的操作一律放在該筆資料的右鍵 `context menu`。

- 例如：編輯、刪除、重新整理、定位、複製值、開啟詳細內容
- 不在表格每列放置獨立按鈕

只有不屬於單筆資料的操作，才考慮以介面按鈕提供。

- 例如：新增、重新整理整個 tab、展開篩選區、切換顯示模式

### 3.4 單一資料操作 dialog 守則

在 GUI 中，任何已由畫面上下文明確鎖定操作目標的單一資料操作 dialog，都不應再顯示 `target` 輸入欄位。

適用情境包含但不限於：

- 左欄搜尋結果右鍵選單開啟的 `新增別名`、`新增網址`、`新增貼文`、`新增工作紀錄`、`設定提醒`
- 右欄各維護 tab 中，針對既有單筆資料開啟的編輯或衍生操作 dialog

此類 dialog 的規則如下：

- 操作目標固定，不允許在 dialog 內切換 target
- dialog title 必須顯示操作目標摘要
- 目標摘要至少應包含 creator 主名稱；必要時可附 `#creator_id`

## 4. 現況與目標差異

### 4.1 現況

目前主畫面主要特徵如下：

- 頂部為工具列按鈕
- 中央區存在多個固定 tab
- 右側詳細區為純文字輸出
- 搜尋結果與詳細資料之間缺乏穩定的「工作區」概念
- 通知訊息為暫時性提示，不符合本次要求的固定停駐模式

### 4.2 目標

調整後主畫面需符合以下方向：

- 以搜尋結果作為左欄入口
- 以右欄綜合詳細視窗作為主要工作區
- 右欄由系統動態管理 tab，使用者只切換與關閉，不自行新增空白 tab
- `overview` 不再是純文字整頁輸出，而是可讀性高、可互動的總覽介面
- 關聯資料的維護應進入各自對應的維護 tab 操作
- 右下角通知區改為固定停駐式訊息區

## 5. 主畫面整體設計

主畫面由以下區塊構成：

- 頂部選單列
- 主畫面 body
- 右下角通知區

### 5.1 主畫面 body 版型

主畫面 body 改為 2 欄：

- 左欄
- 右欄

預設寬度比例為 `1:2`，使用者可隨時拖拉調整寬度。

系統應記住本次執行期間的分隔條位置；是否跨啟動保存可後續另立需求，本文件先不強制。

### 5.2 RWD / 自適應策略

本次調整後的 GUI 必須能在不同大小的視窗中維持可用性與可讀性，不能只針對單一固定尺寸設計。

本系統雖為桌面 GUI，不採網頁式 RWD，但仍需具備自適應版面策略。

基本原則如下：

- 大視窗時，維持左右雙欄與右欄多 tab 的完整工作模式
- 中型視窗時，欄位與卡片可收斂資訊密度，但不得破壞主要操作流程
- 小型視窗時，應優先保證操作可達性與資訊不重疊，而非強行維持原比例

至少需遵守以下行為：

- 左右欄分隔可拖拉
- table 欄位可水平調整，必要時允許水平捲動
- 長文字欄位需截斷顯示，但應保留 tooltip 或可定位到詳細區
- overview 卡片區在寬度不足時可改為上下堆疊
- 最近活動區在寬度不足時可改為單欄列表
- 右下通知區在窄視窗時仍需固定可見，展開後不得超出主視窗可用範圍
- tab 標題在寬度不足時需支援截斷、省略或可捲動，實作策略參考 `docs/sample/hydrus-master-src`
- tab 拖曳排序與 tab 右鍵選單在窄視窗下仍需可操作

本次版本至少要避免：

- 控件重疊
- 文字完全被壓到不可讀
- 主要操作按鈕或右鍵目標不可達
- 通知區把主要內容完全遮住

## 6. 頂部選單列

### 6.1 目標

頂部 bar 應縮小高度，收斂成多個下拉式選單，不再使用目前偏工具列按鈕的主操作模式。

### 6.2 選單結構

頂部只保留以下根節點：

- `新增`
- `設定`

各根節點展開後使用樹狀選單，只有最終節點才觸發功能。

### 6.3 選單內容

`新增`

- `新增創作者`

`設定`

- `介面主題`
- `介面主題 > 預設`
- `介面主題 > 黑暗`

### 6.4 設計說明

- 既有 `新增別名`、`新增網址`、`新增貼文`、`新增工作紀錄`、`設定提醒` 不再保留在頂部主選單
- 上述操作改由左欄搜尋結果右鍵選單與右欄維護 tab 內完成

## 7. 左欄設計

左欄由兩部分組成：

- 頂部搜尋 input
- 下方搜尋結果區

### 7.1 搜尋 input

頂部搜尋 input 保留原樣，搜尋範圍維持查找 creator 主檔與 name 定義。

本次不要求改動搜尋語法與後端搜尋邏輯，只調整結果呈現與後續互動。

### 7.2 搜尋結果欄位

搜尋結果只保留以下欄位：

- `名稱`
- `搜尋匹配`

其中 `搜尋匹配` 欄位的顯示形式如下：

- `平台-<平台名稱>-<匹配名稱或ID>`
- `別名-<匹配名稱>`

若後續需擴充其他匹配型別，需遵守「型別-摘要」格式，以維持一致性。

### 7.3 搜尋結果列互動

搜尋結果單行資料操作如下：

- 單擊左鍵
  - 單純選定資料，不觸發右欄內容切換
- 雙擊左鍵
  - 觸發在右欄開啟對應 creator 的 `Overview` tab
- 單擊右鍵
  - 開啟 `context menu`

### 7.4 搜尋結果右鍵選單

搜尋結果列的右鍵 `context menu` 只需包括：

- `新增別名`
- `新增網址`
- `新增貼文`
- `新增工作紀錄`
- `設定提醒`

此時因為使用者已經選中 target，不再要求填入 `TARGET`。

### 7.5 搜尋結果右鍵選單行為

各選單項目點擊後：

- 由 GUI 層帶入目前選中 creator
- 呼叫既有或新增的 dialog
- dialog 完成後透過 controller / service 執行實際寫入

## 8. 右欄綜合詳細視窗

### 8.1 定位

右欄作為綜合詳細視窗，是使用者查看與維護單一 creator 相關資料的主要工作區。

### 8.2 tab 管理總則

右欄保留上方子 tab UI，但改為由系統管理 tab 的增減。

規則如下：

- 使用者可以切換 tab
- 使用者可以關閉 tab
- 使用者不能自行新增空白 tab
- tab 樣式、長 tab 顯示優化、拖曳排序、tab 右鍵選單完整度應參考 `docs/sample/hydrus-master-src`

### 8.3 tab 開啟策略

採用固定 tab 策略：

- 同一 creator 固定一個 `Overview` tab
- 同一 creator 下可再開以下維護 tab：
  - `URLs`
  - `Aliases`
  - `Posts`
  - `Reminder`
  - `Worklogs`

若同一 creator 的同類型 tab 已存在，系統不重複新增，而是：

- 切換到既有 tab
- 視需要 refresh 該 tab

### 8.4 搜尋結果雙擊規則

雙擊搜尋結果時，一律開啟該 creator 的 `Overview` tab。

若該 `Overview` tab 已存在，系統直接切換至既有 tab 並 refresh。

### 8.5 tab 類型

右欄 tab 類型如下：

- `Overview`
- `URLs`
- `Aliases`
- `Posts`
- `Reminder`
- `Worklogs`

### 8.6 tab 標題規則

右欄 tab 標題需包含 `#creator_id`，以保證多 tab 並存時仍具辨識性。

標題格式至少應符合：

- `<tab類型> - <主名稱> (#<creator_id>)`

實際顯示可依 tab 寬度做截斷或省略，但在 hover tooltip 或其他補充顯示中仍應保留完整資訊。

### 8.7 tab 排序與右鍵選單

右欄 tab 的操作完整度應比照 `docs/sample/hydrus-master-src`。

至少需包含：

- 使用者可拖曳 tab 手動排序
- 長 tab 過多時仍可合理操作
- 提供豐富的 tab 右鍵選單

tab 右鍵選單至少應預留以下能力：

- 關閉目前 tab
- 關閉其他 tab
- 關閉右側 tab
- 依需求提供排序相關功能

若 `hydrus-master-src` 尚有可直接適用於本工具的 tab 管理能力，原則上應一併採納；只有遇到明顯不適合本工具的情況時，才另外提出決策。

## 9. Overview tab 設計

### 9.1 角色

`Overview` 作為單一 creator 的總覽頁，負責提供：

- 主資料摘要
- 關鍵統計
- 最近活動摘要

`Overview` 不負責承載關聯資料維護操作本體。關聯資料的實際 CRUD 應進入各自維護 tab 處理。

### 9.2 畫面結構

`Overview` 採兩段式：

- 摘要區
- 最近活動區

### 9.3 摘要區

摘要區採 `2 欄資訊卡 + 右側操作按鈕列` 的視覺形式。

左側資訊至少顯示：

- 主名稱
- `creator_id`
- 狀態
- 最後更新時間

右側統計卡至少顯示：

- `profile` 數
- `alias` 數
- `URL` 數
- `post` 數
- `worklog` 數
- `reminder` 狀態

摘要區中的統計卡以摘要資訊為主，不在此區直接承擔維護入口責任。

摘要區右側可保留非單筆資料層級的高層次按鈕，但本次不強制規定必須存在；若後續加入，也不得違反「單筆資料操作統一走右鍵選單」守則。

### 9.4 最近活動區

最近活動區採兩塊 compact list：

- `最近貼文`
- `最近工作紀錄`

`最近貼文` 顯示最近 `3 至 5` 筆，欄位建議如下：

- 標題或 URL 摘要
- profile 摘要
- captured 時間
- published 從gdl取得強化資訊後拿到的貼文上傳時間

`最近工作紀錄` 顯示最近 `3 至 5` 筆，欄位建議如下：

- 內容摘要
- 建立時間

### 9.5 最近活動區互動

最近活動區的互動規則如下：

- 點擊最近工作紀錄單筆，可切到 `Worklogs` tab 並定位該筆
- 最近貼文在本次版本先以唯讀摘要顯示，不要求從 overview 直接開獨立貼文維護頁

## 10. 維護 tab 設計

### 10.1 共通原則

各維護 tab 負責關聯資料的實際查看與 CRUD。

各維護 tab 需遵守以下規則：

- 單筆資料操作一律收斂到右鍵 `context menu`
- 非單筆資料操作才考慮放在 tab 內按鈕區
- tab 內不使用「每列一堆小按鈕」的設計

### 10.2 URLs tab

角色：

- 查看與維護該 creator 關聯的網址紀錄

建議 UI：

- 上方工具區
- 下方 table

允許的非單筆操作按鈕：

- `新增`
- `重新整理`

單筆右鍵選單至少預留：

- `關聯的profile摘要` 本項目僅顯示用
- `編輯` 
- `刪除`
- `複製網址`

### 10.3 Aliases tab

角色：

- 查看與維護該 creator 關聯的別名紀錄

建議 UI：

- 上方工具區
- 下方 table

允許的非單筆操作按鈕：

- `新增`
- `重新整理`

單筆右鍵選單至少預留：

- `編輯`
- `刪除`
- `複製名稱`
- `顯示綁定層級資訊`

### 10.4 Posts tab

角色：

- 查看與維護該 creator 關聯的貼文紀錄

建議 UI：

- 上方工具區
- 左或上方列表
- 右或下方 meta history 維護列表 (未開啟時隱藏)
- meta history 位置水平/垂直分割可用按鈕切換

允許的非單筆操作按鈕：

- `新增`
- `重新整理`

單筆右鍵選單至少預留：

- `編輯`
- `刪除`
- `複製貼文網址`
- `顯示詳細資訊` 用 dialog 顯示只讀 json
- `重新取得資訊` 這個會重新呼叫gdl獲取meta，但會保留原有meta，每筆曾經成功獲取過的meta資料都會留存在歷史紀錄中可供查看，且歷史紀錄永不刪除(除非使用者用維護頁面刪除他)

meta history 維護列表單筆資料雙擊: 用 dialog 顯示只讀 json

meta history 維護列表右鍵選單:

- `刪除` 單純用於移除獲取meta的raw紀錄，不連坐修改其他表或欄位

### 10.5 Reminder tab

角色：

- 維護該 creator 的提醒資料

因 reminder 為每位 creator 最多一筆，因此此 tab 可採單筆 detail card 或單筆 detail form 呈現，而非列表型 table。

允許的非單筆操作按鈕：

- `新增`（僅當目前尚無 reminder 時顯示）
- `重新整理`

若目前已有 reminder，則該筆 reminder 的操作仍視為單筆資料操作，需統一透過右鍵 `context menu` 提供。

單筆右鍵選單至少預留：

- `編輯`
- `刪除`

### 10.6 Worklogs tab

角色：

- 查看與維護該 creator 的工作紀錄

建議 UI：

- 上方工具區
- 左或上方列表
- 右或下方 detail preview
- detail preview 位置水平/垂直分割可用按鈕切換

允許的非單筆操作按鈕：

- `新增`
- `重新整理`

單筆右鍵選單至少預留：

- `編輯` 只能改內容，並觸發update時間，created時間不變
- `刪除`

雙擊單筆資料: 顯示在預覽區域，可切換純文字/基本md渲染

## 11. 右下角通知區

### 11.1 目標

所有訊息不應自動消失，且不是一般懸浮 toast，而是右下角固定停駐、貼齊主視窗的通知區。

整體互動與視覺策略參考 `docs/sample/hydrus-master-src` 的 popup toaster / summary bar 模式。

若 `hydrus-master-src` 的通知區作法可直接套用於本工具，原則上應直接對齊；只有遇到明顯不適用於本工具的情況時，才另行提出決策。

### 11.2 預設顯示策略

預設狀態下：

- 只顯示最新一則通知
- 顯示在主畫面右下角
- 緊貼主視窗，而非獨立漂浮到畫面其他位置

### 11.3 展開策略

通知區需提供一個小型展開按鈕。

使用者點擊展開後：

- 顯示完整通知堆疊
- 以 summary bar + 多則通知卡片形式呈現

使用者可再次收合，回到只顯示最新一則的狀態。

### 11.4 訊息存留規則

- 訊息不自動消失
- 使用者可手動關閉單一訊息
- 使用者可透過 summary bar 執行 `dismiss all`

### 11.5 訊息層級

通知區至少支援以下層級：

- `info`
- `warning`
- `error`

## 12. 事件流程

### 12.1 搜尋結果雙擊

1. 使用者在左欄雙擊一筆搜尋結果
2. GUI 取得該列對應的 `creator_id`
3. GUI 檢查右欄是否已有該 creator 的 `Overview` tab
4. 若無則建立新 tab，若有則切換至既有 tab
5. GUI 透過 controller 讀取 snapshot / summary 資料
6. `Overview` tab refresh 顯示

### 12.2 搜尋結果右鍵新增操作

1. 使用者在左欄右鍵點擊某筆搜尋結果
2. GUI 開啟 `context menu`
3. 使用者選擇 `新增別名`、`新增網址`、`新增貼文`、`新增工作紀錄` 或 `設定提醒`
4. GUI 開啟對應 dialog，並自動鎖定目前 creator 為操作目標
5. dialog 不顯示 `target` 欄位，改在 title 顯示固定目標摘要
6. dialog 確認後由 controller / service 寫入
7. 寫入完成後 publish 對應事件
8. 左欄與右欄相關 tab refresh
9. 右下通知區增加新訊息

### 12.3 Overview 切到維護 tab

1. 使用者在 `Overview` 最近活動區點擊可導向的項目
2. GUI 依項目型別開啟或切換到對應維護 tab
3. 維護 tab refresh 並定位對應資料

### 12.4 維護 tab 單筆右鍵操作

1. 使用者在維護 tab 選中單筆資料
2. 使用者右鍵開啟該筆 `context menu`
3. 選擇操作項目
4. 若為 dialog 型操作，dialog 不顯示 `target` 欄位，並在 title 顯示固定目標摘要
5. GUI 呼叫對應 dialog 或行為
6. 成功後 refresh 該 tab 與必要摘要資訊
7. 右下通知區新增結果訊息

## 14. 驗收標準

### 14.1 頂部選單列

- 頂部不再以舊式工具列為主要操作介面
- 使用者可從 `新增 > 新增創作者` 開啟新增創作者功能
- 使用者可從 `設定 > 介面主題` 切換主題

### 14.2 左欄

- 左欄保留搜尋 input
- 搜尋結果欄位只顯示 `名稱` 與 `搜尋匹配`
- 單擊左鍵只選定，不刷新右欄
- 雙擊左鍵會開啟或切換到對應 creator 的 `Overview` tab
- 右鍵選單包含本文件規定的 5 個功能

### 14.3 右欄 tab

- 右欄可由系統開啟 `Overview` / `URLs` / `Aliases` / `Posts` / `Reminder` / `Worklogs`
- 使用者只能切換與關閉 tab，不能自行新增空 tab
- 同一 creator 的同類型 tab 不重複開啟
- tab 標題需包含 `#creator_id`
- 使用者可拖曳 tab 手動排序
- tab 右鍵選單需具備接近 `hydrus-master-src` 的完整度

### 14.4 Overview

- `Overview` 不再使用純文字整頁輸出
- `Overview` 至少包含摘要區與最近活動區
- 最近工作紀錄可導向 `Worklogs` tab

### 14.5 維護 tab

- 關聯資料維護在各自 tab 中進行
- 單筆資料操作統一走右鍵選單
- 非單筆資料操作可使用 tab 內按鈕
- `Posts` 必須有獨立維護 tab

### 14.6 Dialog

- 在 GUI 內由既有上下文鎖定 target 的單一資料操作 dialog，不顯示 `target` 欄位
- dialog title 需顯示固定操作目標摘要

### 14.7 RWD / 自適應

- 在不同視窗尺寸下，主要操作仍可完成
- overview、各維護 tab、通知區在窄視窗下不應出現重疊或不可操作
- 長 tab、長文字、表格欄位在小視窗下仍有合理退化策略

### 14.8 通知區

- 通知區固定在右下角
- 預設只顯示最新一則
- 可展開查看完整通知堆疊
- 通知不自動消失
- 可手動關閉單筆與全部訊息
- 可直接適用於本工具的通知區行為，原則上對齊 `hydrus-master-src`
